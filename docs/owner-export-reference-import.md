# Owner export reference importer acceptance

Issue #250 uses `scripts/owner-export/reference-importer.mjs` as a test-only reference consumer. It has no product route, provider migration behavior, notification writer, Visitor action writer, or access to production services. It accepts published package bytes, runs the pinned offline validator, independently reads bounded ZIP directory entries, and reconstructs the original identities, record values, dependencies, and asset bytes into a fresh PostgreSQL schema and private Storage prefix.

All package, schema compatibility, identity, relationship, and asset digest checks finish before the first target write. The importer reserves a fresh PostgreSQL schema with one autocommit `CREATE SCHEMA`; a collision is rejected before touching Storage. Before each no-upsert upload to an invocation-specific `imports/<uuid>/...` path, it persists an autocommit ownership intent in the reserved schema. Storage metadata carries the matching owner token. This lets a retry recover a committed upload whose response was lost, while checking the exact object metadata prevents deletion of a foreign object that won a key collision. The transaction that publishes reference rows starts only after uploads complete. Cleanup removes exact ledger keys only when their Storage metadata proves ownership; cleanup failures retain the schema, intent, redacted cause, namespace and owner token for retry. `cleanupOwnerExportReference` validates that token and deletes exact ledger paths before dropping its own schema. It never removes a caller-supplied whole namespace or source/winning/foreign objects.

The fresh schema retains the original manifest, parsed source records, byte descriptors and dependency declarations, and also stores an independently built `reference_model` projection and `external_dependencies`. These projections are not produced by the exporter. They interpret:

- Content item and revision identities, localized publication pointers/history, lifecycle-gated public locale/discovery facts, durable route identity/redirect history, and project relationship history.
- Taxonomy value state/history, merge chains and assignment meaning. A merged value resolves to its active meaning; retired values remain historical and do not become assignable by import.
- Media acceptance/publication state, accessibility and exact included byte digests. Non-accepted Media never receives an inferred asset reference.
- CV version identity/history and the explicit current pointer. An absent or null current pointer remains absent/null; activation history does not select a replacement.
- Moderation state with lawful retained text and minimal audit history, plus Analytics goal versions, explicit active pointer, report withholding and retained Configuration.

Rows in `reference_model(kind, identity, value)` are queryable reference facts with stable natural identities. Duplicate identities, dangling included dependencies, invalid current pointers, broken histories, invalid merge targets, missing included Media bytes, and unlawful suppressed text fail before reservation. Dependencies omitted by partial selections remain queryable as explicit external edges; no missing scope or relationship target is silently materialized. For v1.0 Content, the projection keeps only the legacy revision flags and redirect facts: publication history, publication timestamps, canonical slugs, and route reservation history are marked unavailable instead of being inferred. For v1.0 Analytics, activation events are retained without invented sequence numbers; when the manifest has no dependency declarations, included targets are validated and omitted-scope references are marked as inferred legacy edges. Additive package versions keep their supplied facts and declarations.

Dependency checks resolve scope identities, not every UUID nested in a record. When `portfolio-content` is selected, current `relatedProjectIds` and Taxonomy current or historical Project assignments must resolve to an actual Project record, even if their manifest edge says `omitted/not-retained`. Moderation Project references retain their separate documented `not-retained` allowance, and references to unselected scopes remain explicit `scope-not-selected` dependencies.

Run the focused local-service gate with:

```sh
npm run setup:validation
npm run validation:ready
npm run phase8:focus:reference-import
```

The runner starts a task-owned local Supabase Storage project with private buckets and a separate native PostgreSQL cluster with restricted application and worker roles. It exercises the real request, assembly, ready, private download, offline validation, and reference-import path. Source fixture data is synthetic and test-owned; it contains no developer or production data. The composed snapshot path and individual owning-module adapters are exercised against the disposable PostgreSQL cluster.

The gate covers seven single-scope packages, empty selected Content and CV datasets (including no current CV fallback), representative partial scope combinations, a full package, a supported v1.0 flat record, and additive minor-version metadata. It queries the independent reference model for full/partial/legacy goal, history, relationship, current-pointer, discovery and byte semantics; it also checks exact restored asset hashes and lengths, dependency coverage, retention redaction, zero skipped tests, and cleanup. The sanitized local evidence is written to `evidence/phase8-owner-export-reference-import-250.json`.

The all-scope real-service fixture seeds rich Content, Taxonomy, Media, CV, Moderation, Analytics, and Configuration facts, then checks them after request, composite capture, source private Storage reads, assembly and eligibility, download, parsing, and import. The separate hand-built fixture remains a supplemental adversarial model test; it is not the real-service preservation proof. The tests also exercise lifecycle fences with a one-connection pool and concurrent operations saturating the default five-connection pool. These fixtures prove the selected source facts, compatibility behavior, reconstruction boundaries, and cleanup; they do not establish production recovery time, maximum-size throughput, a live schedule, or a supported operational restore procedure. Backup and recovery operations remain in issue #255.
